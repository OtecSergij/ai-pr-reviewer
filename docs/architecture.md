# Architecture and Conventions
## 1. Directory structure

- **`app/` — routing and UI only.** Pages, layouts, route handlers, client components and hooks. No domain or infrastructure logic lives here.
- **`lib/` — all domain and infrastructure logic.** The framework imposes structure only on `app/`; everything else we organize ourselves inside `lib/`.
- **The dependency graph is unidirectional:** `app → components → lib`. `lib/` never imports from `app/`.
- **Organization by domains and boundaries, not by technical layers.** No top-level `services/`, `controllers/`, `models/` folders. Instead: the dominant feature gets a single home, external services hide behind adapters, infrastructure is kept separate.
- **A domain entity has one home.** All states and logic of an entity live next to each other rather than being smeared across several technical folders.

Target skeleton (a folder-level reference, not a strict list):

```
app/            routing, UI, route handlers (thin)
lib/
  review/       the feature's single home: domain model, boundary schemas,
                stream contract, orchestration, tools, prompt
  ai/           LLM infrastructure (provider configuration)
  github/       external service adapter (port + implementation)
  env           environment validation
```

## 2. Boundaries and data translation

- **External boundaries speak their own language, the domain speaks its own.** Sources of external format: the GitHub API and the model-facing (LLM) schemas. Between them and the domain there is always a translation point.
- **Translation happens in the adapter, on entry into the domain.** An external module exposes data already in the domain format; the domain knows nothing about the shape of the external response.
- **`snake_case` is the language of boundaries, `camelCase` is the language of the domain and UI.**
- **The translation criterion:** a value is translated into the domain format if domain or UI logic consumes it; a value stays in the external format if it merely crosses the application from one external boundary to another (for example, data that is only shown to the model and takes no part in domain logic).
- **A type with multiple consumers.** If a value goes both to the domain/UI and to the model, it is stored in the internal format (`camelCase`) and handed to the LLM boundary as a snake_case projection. The format is not chosen "by the majority of fields" or "by the smaller diff": as soon as the UI or the domain consumes the data, the internal type becomes `camelCase` and the projection happens at the boundary.
- **The LLM contract deliberately stays in the external format.** Tool names and their input fields keep a shape that is familiar to the model and stable as an interface. This format is locked inside the tools-and-schemas layer and does not leak deeper into the domain.

## 3. Source of truth for types

- **Uncontrolled runtime input is validated by a schema; the type is inferred from the schema.** The type is not hand-written in parallel with the validation. This covers: incoming HTTP request bodies, data from the model, environment variables.
- **Internal domain structures are described by hand-written types.** If a structure is never parsed anywhere and exists only inside the application, it needs no schema.
- **Semi-trusted boundaries.** When an external source is accessed through a typed client library, trusting its types and narrowing without runtime validation is acceptable — provided the risk of divergence and the blast radius are small. Strict runtime validation is reserved for genuinely uncontrolled sources.
- **One entity — one type per state.** No empty aliases. If two formally different types are structurally identical, they are one type.

## 4. AI/LLM layer

- **Prompts, tool definitions and provider configuration are separate modules,** not inlined into a route or the orchestrator.
- **The model provider sits behind an abstraction.** Model and provider selection is concentrated in one place, which allows swapping them and supporting a fallback without edits across the codebase. An attempt the model ends at its own output limit counts as a too-large failure rather than a success — it is handed to the next candidate like any other hop, and when the last candidate is the one cut short the review is not persisted, because only a review that ran to completion earns a share link.
- **The free chain is Groq → Cerebras → Gemini, ordered by ascending TPM budget** (8k → 30k → ~250k), and the last link is deliberately the widest one on both axes: it is the candidate that has to absorb whatever the earlier links could not finish. Context windows are *not* monotonic along that order (131k → 65k → 1M) — the ordering is by the budget that actually decides admission, not by the window. `lib/ai/provider.test.ts` locks the composition, the declared numbers and the closing-link invariant, branching on chain length because the BYO chain is a single candidate.
- **Cerebras runs `gpt-oss-120b`, chosen on 12.08.2026 against the provider catalog read that day.** The previous pick, `zai-glm-4.7`, has an announced shutdown date of 17.08.2026 ([model card](https://inference-docs.cerebras.ai/models/zai-glm-47)); after it the provider answers 404 and every review would open with a mandatory hop. `gpt-oss-120b` is the only model Cerebras currently lists as Production with confirmed tool calling ([model card](https://inference-docs.cerebras.ai/models/openai-oss)). Its id there is `gpt-oss-120b` — **without** the `openai/` prefix that the same weights carry on Groq. Two links on identical weights are the deliberate choice rather than an oversight: what the hop buys is a different provider and a different quota bucket (8k TPM on free Groq against 30k on the Cerebras trial), not a different model, and on free Groq no tool-capable model offers more than 8k TPM anyway. The price is that the two links are indistinguishable by model id. The failover divider and the failover logs label the **provider** and are therefore unambiguous; the share page is not — `saveReview` persists `candidates[i].modelId` into a column named `provider` and `/r/<slug>` renders it raw, so a stored review now reads either `openai/gpt-oss-120b` or `gpt-oss-120b` with no way to tell which provider produced it. The ambiguity is known and left in place: the column and its rendering belong to the persistence and UI epics, and changing what it stores is a migration decision, not a model-chain one.
- **The output ceiling is a per-candidate field, and on half the candidates it is deliberately absent.** `maxOutputTokens` lives on `ModelCandidate` and `streamText` forwards it as-is, so the premium path keeps the uncapped behavior that was chosen for it on purpose and cannot be capped by an edit at the single call site. Cerebras gets 6_000 and Gemini 24_000; Groq and Anthropic get nothing.
- **Groq is uncapped because on Groq a ceiling is self-inflicted denial of service.** Groq and Cerebras both *reserve* the declared ceiling at admission — the request is checked against the per-minute bucket as input plus the full declared output, before a token is processed. That mechanism is survivable on Cerebras and fatal on Groq purely because of bucket size. Measured against the live API on 12.08.2026: a 78-token prompt to `openai/gpt-oss-120b` on the free tier returns 200 with no `max_tokens` (usage: 78 prompt, 51 completion); the identical prompt with `max_tokens: 8000` returns **413**, `type: "tokens"`, `code: "rate_limit_exceeded"`, body «Request too large for model `openai/gpt-oss-120b` … on tokens per minute (TPM): Limit 8000, Requested 8078, please reduce your message size» — `Requested` is the 78 input tokens plus the 8000 reserved. Any ceiling X on Groq subtracts X from the same 8k that has to hold the transcript: 4k halves the admissible input, 2k truncates an honest closing verdict, 8k rejects every request outright and kills the first link. Leaving it off is safe because the bucket itself bounds a runaway: a step that overruns simply makes the next request 413 and the run hops, and the worst single-request damage is the model's own 65k output ceiling ([model](https://console.groq.com/docs/model/openai/gpt-oss-120b)) out of a 200k daily budget ([limits](https://console.groq.com/docs/rate-limits)).
- **Cerebras is capped at 6_000 because there the same reservation is affordable and useful.** Its trial bucket is 30k TPM, so an explicit 6k reserve leaves a predictable ~24k for input, whereas an absent field lets the provider apply its own upper-bound heuristic and reserve more than we would. Reasoning tokens count against that output budget ([rate limits](https://inference-docs.cerebras.ai/support/rate-limits)).
- **Gemini is capped at 24_000 for the opposite reason — not admission, but the cost of stopping.** It is the closing link, where `finishReason: "length"` is not a hop but a refusal to persist the review, so the ceiling sits three-to-ten times above a typical step and has to leave room for thinking tokens. Google shows no evidence of reserving the declared ceiling at admission, and at a ~250k bucket it would not matter if it did.
- **On the wire the ceiling is `max_tokens` for Cerebras and `generationConfig.maxOutputTokens` for Gemini,** and the two arrive there by different code paths. Cerebras goes through `@ai-sdk/openai-compatible` (`dist/index.mjs:516`); the Cerebras package layers only a `transformRequestBody` that renames `reasoning_content` to `reasoning` and does not touch the ceiling, so it never becomes `max_completion_tokens`. `@ai-sdk/groq` does not depend on `openai-compatible` at all and writes `max_tokens` from its own code (`dist/index.mjs:424`) — the same field name, a separate implementation; that is where a Groq ceiling would land if one were ever set. The same calls carry no `response_format`: `streamText` derives it from an `output` option we do not pass, which matters because Cerebras rejects tools and a response format in one request ([structured outputs](https://inference-docs.cerebras.ai/capabilities/structured-outputs)).
- **`ModelCandidate` states a `contextWindow` and a `tpmBudget`,** the second meaning "the per-minute token budget a transcript has to fit into" — the inputs for a budget pre-flight that the orchestrator does not do yet. Values as of 12.08.2026: Groq `openai/gpt-oss-120b` 131_072 / 8_000 ([model](https://console.groq.com/docs/model/openai/gpt-oss-120b), [limits](https://console.groq.com/docs/rate-limits)); Cerebras `gpt-oss-120b` 65_536 / 30_000 — the trial numbers, because the service runs on the trial, while a paid account would see 131k of context; Gemini 2.5 Flash 1_048_576 / 250_000, where the TPM figure comes from secondary sources since Google no longer publishes free-tier numbers; Anthropic `claude-sonnet-4-6` 1_000_000 ([now the default without a beta header](https://platform.claude.com/docs/en/build-with-claude/context-windows)) / 2_000_000, the Start-tier ITPM taken as a baseline because a BYO key's tier is unknowable.
- **Tools are designed as an interface for the model:** semantic namespaced names, clear field names, error messages as actionable hints, an input schema.
- **The stream contract between backend and frontend has a single source** from which both sides are derived. The message type is not duplicated.
- **Proven mechanics are not rewritten.** If a streaming pattern is confirmed as canonical for the current stack, it stays; only file placement changes.

## 5. Orchestration and routes

- **Route handlers are thin:** validate the input, delegate to the domain orchestrator, return the result. Business logic, limits, provider or mock-mode selection live in the domain layer, not in the route.
- **Server-side logic is marked explicitly.** Modules that work with secrets and external clients are isolated behind a barrier that keeps server code from leaking into the client bundle.
- **Feature configuration is centralized.** Limits and thresholds live in one place instead of being scattered around the code as constants.
- **A review is persisted only against a positive terminal outcome, never against the absence of an error.** The AI SDK ends the step loop the same way whether the model was done or the step ceiling stopped it: when `stopWhen` fires, the `finish` chunk carries the *last step's* `finishReason` and nothing that says the stop condition is what ended the run (`node_modules/ai/dist/index.mjs:7679-7686`). And an abort that lands before a chunk clears the guard produces no `finish` chunk at all: the wrapper re-checks `abortSignal.aborted` after every `reader.read()`, drops the value it just read, enqueues `{type:"abort"}` and closes (`:6967-6990`), while `toUIMessageStream` synthesizes nothing in its place (`:8098-8111`) — a `finish` already past that check still arrives, so the missing reason is a possibility to handle rather than a guarantee. So "no error, therefore success" is wrong twice over: a run is saved only when it reported a terminal `finishReason` other than `length` and the last step did not trip the exhaustion flag the next point describes; an attempt that trips either hops to the next candidate, and on the last candidate the review is not saved and gets no share link — the share page can only show a review that ran to completion.
- **Exhaustion is recognized by the shape of the last step, not by a reason string.** The loop continues only while the last step left client tool calls that were all executed, and stops there as soon as `stopWhen` is met (`:7646-7655`) — so exiting *with* client tool calls in the final step means the ceiling is what ended the run, while an honest finish is a text step with no tool calls. `onStepFinish` therefore records `step.toolCalls.some(call => call.providerExecuted !== true)` next to the step count, and exhaustion is that flag together with `steps >= MAX_STEPS`; a run that genuinely ends on its 60th step cannot false-positive, and for the BYO chain (`stopWhen: () => false`) the flag is dead by construction, which is correct — there is no ceiling to exhaust. Reason strings cannot carry this: `finish_reason` is passed through verbatim by `@ai-sdk/groq` (`dist/index.mjs:346-361`) and `@ai-sdk/openai-compatible` (`dist/index.mjs:304-318`), and only `@ai-sdk/google` guards it with `hasToolCalls`, so a backend that answers `stop` alongside `tool_calls` defeats `finishReason === "tool-calls"` and `finishReason !== "stop"` alike.
- **The client is told when a finished-looking review will get no share link, because it cannot work that out itself.** Exhaustion reaches the browser looking positive — the `finish` chunk carries the last step's reason, `stop` or `tool-calls` — so a client keyed on `finishReason` alone would render "Review complete" for a run the server just refused to persist; and a save that was attempted and failed is indistinguishable from one that was never attempted, since both simply produce no `data-share`. Both facts exist only on the server, so the terminal `data-outcome` part states them: `incomplete` drives the cut-short heading, `saveFailed` the "couldn't create a share link" notice. The notice deliberately does not claim the review was not saved — `saveReview` races the insert against a timeout and losing that race does not cancel the statement, so a row may still land afterwards; it says only that there is no link and that a re-run is what produces one. A save that was skipped rather than attempted (private, stopped, mock) says nothing at all.

## 6. Configuration and environment

- **Everything that changes between deployments** (secrets, keys, hosts, flags) goes through environment variables, not code.
- **The environment is validated at startup** with a typed schema, fail-fast: a missing or invalid value crashes the app immediately with a clear error instead of failing later, mid-operation.
- **No external dependency is introduced for configuration** while a hand-written solution covers the need.
- **The client IP comes from the proxy only where a proxy is trusted.** With `TRUST_PROXY=1` the limiter takes the rightmost `X-Forwarded-For` entry — the one the trusted edge appended, so a client-supplied header cannot spoof it — and every deployment behind Traefik/Coolify must set it. Left empty (the local-dev default) all requests are counted under a single `"dev"` bucket, i.e. one shared quota for the whole internet, so an unset value in production is a misconfiguration rather than a safe default; a typo such as `TRUST_PROXY=true` is rejected at startup by the `z.enum(["1","0",""])` schema instead of silently degrading.
- **The per-IP rate limiter fails open.** If Redis is unavailable, or the check errors or times out, the request is allowed rather than blocked — availability of the review flow is deliberately prioritized over rate limiting during a Redis outage. The connection is awaited with a bounded timeout so a healthy-but-not-yet-connected Redis is used rather than bypassed for the first, sequential request; concurrent requests arriving during the brief sub-second cold-start connect window can still fail open before the first connection resolves — a bounded window that occurs at most once per process and is consistent with the deliberate fail-open, not a fully-eliminated bypass. Failures are logged rather than swallowed so the open state stays visible.
- **Database migrations run in the container entrypoint, serialized by a session-level advisory lock.** The entrypoint applies pending Drizzle migrations before it starts the server. To stop two replicas — or two overlapping zero-downtime deploys — from racing the same non-idempotent DDL (`CREATE TABLE "reviews"` has no `IF NOT EXISTS`), `migrate()` is wrapped in a blocking `pg_advisory_lock(MIGRATION_LOCK_KEY)` taken on the shared `max: 1` postgres-js connection: one physical connection means the session-level lock covers both the `__drizzle_migrations` read and the DDL, so `sql.reserve()` is unnecessary. The loser blocks until the winner releases, then re-reads the migration journal and applies nothing — idempotency comes for free. The key is a fixed integer constant, sent as an untyped parameter that resolves to the sole single-argument `pg_advisory_lock(bigint)` overload by arity. The trade-off is deliberate: migrate-in-entrypoint plus an advisory lock, rather than a one-shot pre-deploy migration job — it is simpler, lives entirely in the repository, and holds up under scale-out.
- **The container is deliberately allowed to look `unhealthy` while it migrates.** `--start-period=30s` plus `--retries=3` × `--interval=10s` gives roughly 60 seconds before the mark, and the entrypoint runs migrations before it binds the port, so the probe does fail for that whole stretch. The mark is informational here rather than actionable: outside Swarm, Docker does nothing with `unhealthy`, and this deployment is a single Coolify-managed container. The one realistic path past 60 seconds is a deploy blocking on the `pg_advisory_lock` above while an overlapping deploy holds it — a case already accepted as deliberate — and widening the budget to 120s would only trade it for a genuinely broken container sitting in `starting` for two minutes. The budget stays at 30s.
- **The base image stays on the floating `node:26-slim` tag, with no digest pin.** Pinning a digest is only worth it together with automated base-image updates: without Renovate or Dependabot it freezes the base image *and its CVEs*, which is a false sense of security rather than a supply-chain control. The price accepted instead is that builds are not bit-reproducible — "green yesterday" does not guarantee "green today" at unchanged code. Revisit the pin only if automated updates land.
- **CI builds the image once and pushes exactly what it smoke-tested.** A single `build-push-action` with `load: true` carries the `metadata-action` tags and labels, the smoke tests run against that loaded image, and a plain `docker push` then ships those same tags. The previous shape built twice — once to load, once to push — and while the file layers were identical, the pushed config blob differed by tags and OCI labels, so the object in the registry was never literally the object that was tested. This closes off the path to multi-arch images, which is accepted: production is one amd64 VPS.
- **The smoke test runs in two phases, because a single phase could only ever prove the migration guard.** With no environment at all the entrypoint short-circuits at `node migrate.mjs`, so `--import ./validate-startup.mjs` never loads and no breakage of the preload could fail the test. Phase one keeps that check and asserts the migration's own message; phase two hands the container a real Postgres and no model keys, so the migration applies and the preload is what fails — asserted on the `validate-startup.mjs` frame in stderr, which the `instrumentation.ts` second net cannot produce. Phase two runs detached behind a bounded wait: with the preload wired out of the entrypoint Next does not crash, it retries the instrumentation hook indefinitely, so a blocking `docker run` would hang the job rather than fail it. The workflow guard is `grep -q -- '--import ./validate-startup.mjs' Dockerfile`; the bare `validate-startup.mjs` it replaced also matched the `COPY` line and passed even with the flag deleted from the entrypoint.
- **PID 1 in the container is `tini`, not the shell.** The entrypoint is `tini -g -- sh -c "node migrate.mjs && exec node … server.js"`, so `tini` reaps zombies and forwards signals to the child's entire process group (`-g`). Without it, during the migrate phase the intermediate `sh` is PID 1 and swallows `SIGTERM` — the `exec` that hands PID 1 to the server only happens on the second half — so a `docker stop` or redeploy mid-migration would hang until `SIGKILL`. Group-mode signalling reaches `node migrate.mjs` directly, so shutdown during a migration terminates cleanly instead.

## 7. Observability and security headers

- **Structured logs in the review flow go to stdout as JSON** through a single `pino` logger (`lib/log.ts`, behind the `server-only` barrier) — no extra env var: the switch is `NODE_ENV` alone, production writing raw JSON with no transport while development pipes the same records through `pino-pretty` (a devDependency) purely for readability. Errors are passed as raw objects at the call sites and sanitized centrally by a custom `err` serializer that wraps `pino`'s standard one: it strips the AI SDK's `requestBodyValues` (the full prompt — the private diff and file contents) and `responseBody` recursively (top level, the `aggregateErrors` array and any nested error/`cause` object) while keeping type, message, stack, status and the cause chain. Without this, a routine provider 429/529 during a private-PR failover would write the private code to stdout (which Coolify persists), breaking the "private reviews aren't persisted" guarantee. The Redis client and the rate limiter log through that same instance as `component`-tagged child loggers, so a Redis socket failure or a fail-open rate-limit check arrives as JSON on stdout next to the review flow instead of flat `util.inspect` text on stderr. A 30-second per-signature window in `lib/redis.ts` collapses a flapping connection into one line plus a `suppressed` count. The Coolify container captures both stdout and stderr and owns aggregation.
- **Every review carries a `requestId`,** generated at the route boundary (honoring an incoming `X-Request-Id` header) and threaded as a `pino` child logger through the orchestrator and into the model tools, so a request's failover, DB-save and enrichment logs correlate under one id.
- **The previously silent failure sites now leave a trace:** a failed `saveReview` (the share link silently never appears), provider failover and final exhaustion, and an enrichment snippet that couldn't be built.
- **A run ends in one of three terminal events, and they are not interchangeable:** `review finished` carries the slug and is written only when the review is actually in the database; `review not saved` carries the reason it is not (`private`, `aborted`, `truncated`, `mock`, `save-failed`); `review failed after providers exhausted` covers the runs that ended on an error. The first two carry the same context — provider, issue count, `finishReason`, step count, duration — so a run stopped at the step ceiling is distinguishable from one that hit the output limit without reading the message string. One path leaves no terminal line at all, and it is a known gap rather than a design: an abort that surfaces as a classified `aborted` failure returns silently. Previously `review finished` was written for every run that did not throw, including the ones that were deliberately never persisted.
- **Every model step logs its token usage** — input, output, reasoning and total — next to its step number, the provider, the model id and the ceiling that step ran under. The UI only ever sees the running total, so without this line the output ceilings would stay guesses; the log is what turns them into a per-step distribution the numbers can be revisited against. It is emitted at `info` deliberately: production runs `pino` at `info`, and a `debug` line would never be collected where the data actually accumulates.
- **Uncaught server and render errors funnel through `onRequestError`** in the root `instrumentation.ts` — the single capture point that logs the error, its `digest` and the route context. It is guarded to the Node.js runtime so the `pino` import never reaches an edge bundle. The share-page client `error.tsx` surfaces that `digest` in its UI so a user can quote it and correlate their report with the server log.
- **Error-tracking (Sentry/GlitchTip) is deliberately deferred** behind the `onRequestError` seam: the choke point exists, the external dependency and DSN do not, until prod volume justifies them.
- **A nonce-based strict CSP is set per request in `proxy.ts`** (the Next 16 rename of `middleware.ts`), the industry-standard approach recommended by Next.js, OWASP and web.dev. Each request gets a fresh CSPRNG nonce; the nonce is put on the request so Next stamps it onto its own framework and bundle scripts, and the same `Content-Security-Policy` is set on the response. `script-src` is `'self' 'nonce-…' 'strict-dynamic'`: `'strict-dynamic'` discards host allowlists and trusts only the nonced bootstrap plus whatever it loads, so an injected `<script>` without the unguessable nonce cannot run. The app is already dynamic per request (mock/real reviews, DB-backed share pages), so the dynamic-rendering that nonces require costs us almost nothing — the root layout `await connection()`s, opting every route into per-request rendering so each gets a fresh nonce (a client-component page such as the home screen cannot host `connection()` itself, and `export const dynamic` is ignored there, so the shared layout is the single correct choke point).
- **`style-src` is `'self' 'unsafe-inline'` with no nonce, deliberately.** Shiki paints syntax tokens with inline `style="color:…"` attributes and the UI uses React `style={{}}`; a nonce cannot cover style *attributes*, and per spec a browser that sees both a nonce and `'unsafe-inline'` in `style-src` ignores `'unsafe-inline'`, which would silently break highlighting. Inline styles cannot execute code, so this is a low risk. `'wasm-unsafe-eval'` stays in `script-src` for Shiki's Oniguruma WASM; `'unsafe-eval'` is added only in development (React refresh/HMR needs it) and never ships to production.
- **Flat, static headers live in `next.config.ts` `headers()` on `/(.*)`** so they cover every response including static assets that the CSP matcher skips: `X-Frame-Options: DENY` and CSP `frame-ancestors 'none'` together forbid framing (clickjacking); `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; a `Permissions-Policy` that turns off clearly-unused features (camera, microphone, geolocation, payment, usb, motion sensors) while deliberately leaving clipboard alone because the copy button uses `navigator.clipboard.writeText`; and `Cross-Origin-Opener-Policy`/`Cross-Origin-Resource-Policy` set to `same-origin` (COEP is intentionally omitted — `require-corp` would break subresources).
- **HSTS is `max-age=63072000; includeSubDomains` without `preload`.** Preloading is near-irreversible (removal from the browser preload list takes months), so it is left off deliberately. If the edge (Traefik/Coolify) already emits HSTS, drop the app-level header to avoid a duplicate.
- **The private-PR gate returns 403 (not 404)** for an anonymous request against a private PR that the server `GITHUB_PAT` can read, which discloses the repository's existence to an anonymous prober. This is an accepted trade-off, not a fix left undone: the primary control is scoping `GITHUB_PAT` to `public_repo` (per `.env.example`), under which GitHub returns 404 for every private repo, the metadata fetch never surfaces a private PR, and this branch is never reached. Given that scoping, the 403-with-private-card response is kept deliberately for its clearer UX.

## 8. Naming

- **Files and folders** — `kebab-case`.
- **Types and interfaces** — `PascalCase`, no `I` prefix.
- **Fields** — `camelCase` in the domain and UI; `snake_case` only at external boundaries.
- **Components** — file in `kebab-case`, export in `PascalCase`. **Hooks** — `use` prefix.
- **Factories** — a single prefix (`create`).
- **Role suffixes in file names** (for example, for schemas) — selectively, only where the file's role is otherwise unclear. Co-location by default, without extracting types wholesale into separate files.
- **Constants** — `UPPER_SNAKE_CASE`. **Model tool names** — `snake_case`, namespaced.

## 9. What we deliberately don't do

Anti-overengineering for a project of the current size (one dominant feature):

- **No** `features/` or `src/` — an extra layer for a single-feature app.
- **No full hexagon / DDD** with use-case layers and behavior-rich domain classes: the entities have no invariants, this is data-in / data-out. Ports exist only for external services.
- **No centralized types folder** — co-location next to the code.
- **No barrel files** in client paths; they are acceptable only as the public entry point of a server-only module.
- **No abstractions or dependencies added in advance** — they are introduced when the simple solution is no longer enough.
