# Architecture and Conventions

## 1. Directory structure

- **`app/` — routing and UI only.** Pages, layouts, route handlers, client components and hooks. No domain or infrastructure logic lives here.
- **`lib/` — all domain and infrastructure logic.** The framework imposes structure only on `app/`; everything else we organize ourselves inside `lib/`.
- **The dependency graph is unidirectional:** `app → components → lib`. `lib/` never imports from `app/`.
- **Organization by domains and boundaries, not by technical layers.** No top-level `services/`, `controllers/`, `models/` folders. Instead: the dominant feature gets a single home, external services hide behind adapters, infrastructure is kept separate.
- **A domain entity has one home.** All states and logic of an entity live next to each other rather than being smeared across several technical folders.

Target skeleton (a folder-level reference, not a strict list):

```
app/            routing, UI, route handlers (thin)
lib/
  review/       the feature's single home: domain model, boundary schemas,
                stream contract, orchestration, tools, prompt
  ai/           LLM infrastructure (provider configuration)
  github/       external service adapter (port + implementation)
  db/           persistence: Postgres client, schema, share-link store
  highlight/    the Shiki highlighter behind the rendered code snippets
  env           environment validation
```

## 2. Boundaries and data translation

- **External boundaries speak their own language, the domain speaks its own.** Sources of external format: the GitHub API and the model-facing (LLM) schemas. Between them and the domain there is always a translation point.
- **Translation happens in the adapter, on entry into the domain.** An external module exposes data already in the domain format; the domain knows nothing about the shape of the external response.
- **`snake_case` is the language of boundaries, `camelCase` is the language of the domain and UI.**
- **The translation criterion:** a value is translated into the domain format if domain or UI logic consumes it; a value stays in the external format if it merely crosses the application from one external boundary to another (for example, data that is only shown to the model and takes no part in domain logic).
- **A type with multiple consumers.** If a value goes both to the domain/UI and to the model, it is stored in the internal format (`camelCase`) and handed to the LLM boundary as a snake_case projection. The format is not chosen "by the majority of fields" or "by the smaller diff": as soon as the UI or the domain consumes the data, the internal type becomes `camelCase` and the projection happens at the boundary.
- **The LLM contract deliberately stays in the external format.** Tool names and their input fields keep a shape that is familiar to the model and stable as an interface. This format is locked inside the tools-and-schemas layer and does not leak deeper into the domain.

## 3. Source of truth for types

- **Uncontrolled runtime input is validated by a schema; the type is inferred from the schema.** The type is not hand-written in parallel with the validation. This covers: incoming HTTP request bodies, data from the model, environment variables.
- **Internal domain structures are described by hand-written types.** If a structure is never parsed anywhere and exists only inside the application, it needs no schema.
- **Semi-trusted boundaries.** When an external source is accessed through a typed client library, trusting its types and narrowing without runtime validation is acceptable — provided the risk of divergence and the blast radius are small. Strict runtime validation is reserved for genuinely uncontrolled sources.
- **One entity — one type per state.** No empty aliases. If two formally different types are structurally identical, they are one type.

## 4. AI/LLM layer

- **Prompts, tool definitions and provider configuration are separate modules,** not inlined into a route or the orchestrator.
- **The model provider sits behind an abstraction.** Model and provider selection is concentrated in one place, which allows swapping them and supporting a fallback without edits across the codebase. An attempt the model ends at its own output limit counts as an `output-truncated` failure rather than a success — it is handed to the next candidate like any other hop, and when the last candidate is the one cut short the review is not persisted, because only a review that ran to completion earns a share link.
- **The free chain is Groq → Cerebras → Gemini, ordered by ascending TPM budget** (8k → 30k → ~250k), and the last link is deliberately the widest one on both axes: it is the candidate that has to absorb whatever the earlier links could not finish. Context windows are _not_ monotonic along that order (131k → 65k → 1M) — the ordering is by the budget that actually decides admission, not by the window. `lib/ai/provider.test.ts` locks the composition, the declared numbers and the closing-link invariant, branching on chain length because the BYO chain is a single candidate.
- **Cerebras runs `gpt-oss-120b`, chosen on 12.08.2026 against the provider catalog read that day.** The previous pick, `zai-glm-4.7`, has an announced shutdown date of 17.08.2026 ([model card](https://inference-docs.cerebras.ai/models/zai-glm-47)); after it the provider answers 404 and every review would open with a mandatory hop. `gpt-oss-120b` is the only model Cerebras currently lists as Production with confirmed tool calling ([model card](https://inference-docs.cerebras.ai/models/openai-oss)). Its id there is `gpt-oss-120b` — **without** the `openai/` prefix that the same weights carry on Groq. Two links on identical weights are the deliberate choice rather than an oversight: what the hop buys is a different provider and a different quota bucket (8k TPM on free Groq against 30k on the Cerebras trial), not a different model, and on free Groq no tool-capable model offers more than 8k TPM anyway. The price is that the two links are indistinguishable by model id. The failover divider and the failover logs label the **provider** and are therefore unambiguous; the share page is not — it renders the stored model id raw, so a stored review reads either `openai/gpt-oss-120b` or `gpt-oss-120b` with no way to tell which provider produced it. What has been resolved since is only the naming: the column is `model_id` rather than `provider` (§6), so it no longer claims to hold something it never held. The ambiguity itself stays, because removing it means persisting the provider as a second column and nothing in the product reads one yet.
- **The output ceiling is a per-candidate field, and on half the candidates it is deliberately absent.** `maxOutputTokens` lives on `ModelCandidate` and `streamText` forwards it as-is, so the premium path keeps the uncapped behavior that was chosen for it on purpose and cannot be capped by an edit at the single call site. Cerebras gets 6_000 and Gemini 24_000; Groq and Anthropic get nothing. The step ceiling has the same shape and the same asymmetry: `stopWhen` is `stepCountIs(MAX_STEPS)` — 60, in `lib/review/config.ts` — on every server candidate and `() => false` on the BYO one, which therefore runs under no step ceiling at all, deliberately, because the key that pays for the extra steps is the user's own.
- **Groq is uncapped because on Groq a ceiling is self-inflicted denial of service.** Groq and Cerebras both _reserve_ the declared ceiling at admission — the request is checked against the per-minute bucket as input plus the full declared output, before a token is processed. That mechanism is survivable on Cerebras and fatal on Groq purely because of bucket size. Measured against the live API on 12.08.2026: a 78-token prompt to `openai/gpt-oss-120b` on the free tier returns 200 with no `max_tokens` (usage: 78 prompt, 51 completion); the identical prompt with `max_tokens: 8000` returns **413**, `type: "tokens"`, `code: "rate_limit_exceeded"`, body «Request too large for model `openai/gpt-oss-120b` … on tokens per minute (TPM): Limit 8000, Requested 8078, please reduce your message size» — `Requested` is the 78 input tokens plus the 8000 reserved. Any ceiling X on Groq subtracts X from the same 8k that has to hold the transcript: 4k halves the admissible input, 2k truncates an honest closing verdict, 8k rejects every request outright and kills the first link. Leaving it off is safe because the bucket itself bounds a runaway: a step that overruns simply makes the next request 413 and the run hops, and the worst single-request damage is the model's own 65k output ceiling ([model](https://console.groq.com/docs/model/openai/gpt-oss-120b)) out of a 200k daily budget ([limits](https://console.groq.com/docs/rate-limits)).
- **Cerebras is capped at 6_000 because there the same reservation is affordable and useful.** Its trial bucket is 30k TPM, so an explicit 6k reserve leaves a predictable ~24k for input, whereas an absent field lets the provider apply its own upper-bound heuristic and reserve more than we would. Reasoning tokens count against that output budget ([rate limits](https://inference-docs.cerebras.ai/support/rate-limits)).
- **Gemini is capped at 24_000 for the opposite reason — not admission, but the cost of stopping.** It is the closing link, where `finishReason: "length"` is not a hop but a refusal to persist the review, so the ceiling sits three-to-ten times above a typical step and has to leave room for thinking tokens. Google shows no evidence of reserving the declared ceiling at admission, and at a ~250k bucket it would not matter if it did.
- **On the wire the ceiling is `max_tokens` for Cerebras and `generationConfig.maxOutputTokens` for Gemini,** and the two arrive there by different code paths. Cerebras goes through `@ai-sdk/openai-compatible` (`dist/index.mjs:516`); the Cerebras package layers only a `transformRequestBody` that renames `reasoning_content` to `reasoning` and does not touch the ceiling, so it never becomes `max_completion_tokens`. `@ai-sdk/groq` does not depend on `openai-compatible` at all and writes `max_tokens` from its own code (`dist/index.mjs:424`) — the same field name, a separate implementation; that is where a Groq ceiling would land if one were ever set. The same calls carry no `response_format`: `streamText` derives it from an `output` option we do not pass, which matters because Cerebras rejects tools and a response format in one request ([structured outputs](https://inference-docs.cerebras.ai/capabilities/structured-outputs)).
- **`ModelCandidate` states a `contextWindow` and a `tpmBudget`,** the second meaning "the per-minute token budget a transcript has to fit into" — the inputs for the budget pre-flight described in §5. Values as of 12.08.2026: Groq `openai/gpt-oss-120b` 131_072 / 8_000 ([model](https://console.groq.com/docs/model/openai/gpt-oss-120b), [limits](https://console.groq.com/docs/rate-limits)); Cerebras `gpt-oss-120b` 65_536 / 30_000 — the trial numbers, because the service runs on the trial, while a paid account would see 131k of context; Gemini 2.5 Flash 1_048_576 / 250_000, where the TPM figure comes from secondary sources since Google no longer publishes free-tier numbers; Anthropic `claude-sonnet-4-6` 1_000_000 ([now the default without a beta header](https://platform.claude.com/docs/en/build-with-claude/context-windows)) / 2_000_000, the Start-tier ITPM taken as a baseline because a BYO key's tier is unknowable.
- **`maxRetries` is a per-candidate field too, and only the closing link is allowed to retry.** The SDK's default is 2 (`node_modules/ai/dist/index.mjs:2739`) and `retry` wraps _every_ `doStream` inside the step loop (`:7284`), so the untouched default meant up to three attempts per step against a per-minute bucket the previous attempt had just proved empty — and because a `retry-after` of 60 or more is discarded in favour of the exponential delay (`:2623-2650`), those three attempts land inside six seconds of a window that stays shut for a minute. Our retry mechanism is the chain itself, so every non-final server candidate declares `maxRetries: 0` and swipes instantly. The field is absent on the closing link and on the BYO candidate, where a single transient 500 has nowhere to hop and killing the run over it would be worse than one re-send; `undefined` is indistinguishable from omitting the key (`:2739`), so absence _is_ the SDK default. `maxRetries: 0` is also the one path that rethrows the provider error raw instead of wrapping it in `RetryError` (`:2675-2677`), which `classifyFailure` already handles because it unwraps `RetryError` rather than requiring it. The invariant lives in `lib/ai/provider.test.ts` rather than at the call site so a future reordering of the chain cannot quietly leave a middle link retrying.
- **Every provider request goes through one wrapper that traces it and bounds its first byte** (`lib/ai/provider-fetch.ts`, passed as `fetch` to all four factories). It exists because the SDK offers no other seam on an individual attempt: `onError` fires once, after the retry loop has given up (`node_modules/ai/dist/index.mjs:6718-6719`), so intermediate failures — and every _successful_ retry — used to leave no trace at all. The wrapper writes one `info` line per attempt with the provider, the host, the status, the `retry-after` header and the duration, and never the body. It also races the response headers against a 20-second timer: **20 s** sits above the slowest legitimate first byte we see (Gemini 2.5 Flash, thinking enabled, on a ~40k-token inherited transcript) with margin, and far below undici's 300-second `headersTimeout`, which was the only previous bound and is long enough to outlive the user. Timing stops when the headers arrive, not when the body ends, so a slow stream is never cut off mid-review.
- **The TTFB timeout is expressed as a synthetic `APICallError`, not as an abort, and that distinction is the whole point.** `streamText`'s own `timeout`/`chunkMs` aborts through a controller merged into the run's `abortSignal` (`node_modules/ai/dist/index.mjs:6530-6544`), and an abort emits `{type:"abort"}` and closes the stream without an `error` part (`:6968-6977`) — `onError` never fires, `failure` stays null, and the orchestrator would take the _success_ branch on a half-read review. Throwing instead is safe because `handleFetchError` passes anything that is not an abort or a `TypeError: fetch failed` straight through (`node_modules/@ai-sdk/provider-utils/dist/index.mjs:499-529`), so our error reaches the retry layer with `isRetryable: false` intact and is never slept on. The error carries status 504 plus a private marker in its message, and `classifyFailure` matches on **both** — a real gateway 504 from a provider is a different event and still classifies as `server`. Note that `isRetryable` defaults to `408 || 409 || 429 || >= 500` when omitted (`node_modules/@ai-sdk/provider/dist/index.mjs:52-56`), so passing it explicitly is required, not decorative. The wrapper composes the SDK's signal with its own timer and checks the SDK's first: when the user presses Stop, the original `AbortError` is rethrown untouched, because that is what keeps the run in the "user cancelled" branch instead of the failure branch.
- **Tools are designed as an interface for the model:** semantic namespaced names, clear field names, error messages as actionable hints, an input schema.
- **A patch too large for one answer is paginated, not truncated.** `get_diff` used to keep hunks while they fitted `PATCH_CAP` and report `patch_truncated: true` — while its own description told the model not to judge a change it had only partly seen, and nothing could serve the rest: the patch comes from the memoised `ensureFiles` map, so a second call returned the same bytes, and a first hunk over the cap produced an empty result reported as `too_large`, i.e. a file that could not be read at all. It now answers `{patch, part, total_parts, has_more, next_part}`, with parts cut at hunk boundaries by the pure `splitPatch` (`lib/review/tools/paginate-patch.ts`), numbered from 1, and `part` omitted meaning the first — weak models drop optional arguments, so the default has to be the useful one. `get_pr_files_summary` publishes `diff_parts` per file, so the reading can be planned before the first `get_diff`. The fix costs zero additional GitHub requests because the full patches are already in that map, parts are deterministic within a request and stable under `headSha`, and they survive a provider hop because tool results pass through `sanitizeForHandoff`.
- **A hunk larger than a part is served whole, over the cap, and that is the safe branch.** Splitting inside a hunk means synthesising an `@@` header, and a header wrong by a single line would not fail loudly: `emit_issue` takes line numbers from the header the model read, while `enrichIssue` searches the _untouched_ patch by range overlap (`lib/review/enrich-issue.ts`), so it would still match a real hunk, highlight the wrong lines and point `blobUrl` past the issue — a silent anchor shift rather than an error. Intra-hunk splitting therefore waits for unit tests on the `@@` arithmetic of both sides; until then an oversized hunk is its own part and exceeds `PATCH_PART_CHARS` deliberately, which is also what keeps the guarantee that no file is left completely unread.
- **Reading is budgeted, and the budget is the first ceiling there has ever been.** Three limits sit in the closure of `createReviewTools`, so they span a whole run including a failover: `MAX_PARTS_PER_FILE` parts of any one file, `PATCH_READ_BUDGET_CHARS` of distinct patch text across the review, and the same `(file, part)` _asked for_ at most `MAX_PART_REPEATS` times. The third limit counts requests rather than answers on purpose: a guard that only counted successful reads would leave a refused part free to be asked for forever, which on the BYO chain (`stopWhen: () => false`) has no step ceiling behind it to stop the loop. So a part refused as `generated` or over the file allowance escalates to `repeat` on the fourth try and stays there, while whether the run's character budget was charged is tracked separately — a part is paid for once, and every later request for it, served or refused, costs nothing. Refusals are statuses, never errors — `part_limit` with a `scope` of `file`, `run`, `generated` or `repeat`, and `no_such_part` carrying `total_parts` — so a refusal reads as information rather than as a failure to retry, and `next_part: null` beside `has_more: true` says "there is more and you may not have it" without inviting the call. The counter that refuses the fourth identical request is what kills the observed re-reading loop, where every pass added ~4 000 characters to a transcript that grew without any bound at all. The point is not that the previous worst case is preserved — it is that until now there was no worst case to preserve.
- **The stream contract between backend and frontend has a single source** from which both sides are derived. The message type is not duplicated.
- **Proven mechanics are not rewritten.** If a streaming pattern is confirmed as canonical for the current stack, it stays; only file placement changes.

## 5. Orchestration and routes

- **Route handlers are thin:** validate the input, delegate to the domain orchestrator, return the result. Business logic, limits, provider or mock-mode selection live in the domain layer, not in the route.
- **Server-side logic is marked explicitly.** Modules that work with secrets and external clients are isolated behind a barrier that keeps server code from leaking into the client bundle.
- **The thresholds that shape the model's input live in one place; the ones that shape a client's behaviour live next to it.** `lib/review/config.ts` holds what decides how much of a PR the model gets to see — `MAX_CHANGED_FILES`, `PATCH_PART_CHARS`, `BODY_CAP`, `MAX_FILE_CONTENTS_BYTES`, the reading budgets and `MAX_STEPS` — because those are product decisions that have to be read together: a patch cap is per file and a body cap is per PR, so comparing them means knowing both. Retry backoffs, socket and statement timeouts stay beside their consumer, where the number only means anything next to the call it bounds. The pure functions keep their purity: `splitPatch` and `truncateBody` take the cap as an argument and default it from `config.ts`, so a test can state its own cap instead of copying a literal — the previous `truncate-patch` test held a hand-written copy of `PATCH_CAP` and would have started asserting against a stale number the moment the real one moved.
- **A review is persisted only against a positive terminal outcome, never against the absence of an error.** The AI SDK ends the step loop the same way whether the model was done or the step ceiling stopped it: when `stopWhen` fires, the `finish` chunk carries the _last step's_ `finishReason` and nothing that says the stop condition is what ended the run (`node_modules/ai/dist/index.mjs:7679-7686`). And an abort that lands before a chunk clears the guard produces no `finish` chunk at all: the wrapper re-checks `abortSignal.aborted` after every `reader.read()`, drops the value it just read, enqueues `{type:"abort"}` and closes (`:6967-6990`), while `toUIMessageStream` synthesizes nothing in its place (`:8098-8111`) — a `finish` already past that check still arrives, so the missing reason is a possibility to handle rather than a guarantee. So "no error, therefore success" is wrong twice over: a run is saved only when it reported a terminal `finishReason` other than `length` and the last step did not trip the exhaustion flag the next point describes; an attempt that trips either hops to the next candidate, and on the last candidate the review is not saved and gets no share link — the share page can only show a review that ran to completion.
- **Exhaustion is recognized by the shape of the last step, not by a reason string.** The loop continues only while the last step left client tool calls that were all executed, and stops there as soon as `stopWhen` is met (`:7646-7655`) — so exiting _with_ client tool calls in the final step means the ceiling is what ended the run, while an honest finish is a text step with no tool calls. `onStepFinish` therefore records `step.toolCalls.some(call => call.providerExecuted !== true)` next to the step count, and exhaustion is that flag together with `steps >= MAX_STEPS`; a run that genuinely ends on its 60th step cannot false-positive, and for the BYO chain (`stopWhen: () => false`) the flag is dead by construction, which is correct — there is no ceiling to exhaust. Reason strings cannot carry this: `finish_reason` is passed through verbatim by `@ai-sdk/groq` (`dist/index.mjs:346-361`) and `@ai-sdk/openai-compatible` (`dist/index.mjs:304-318`), and only `@ai-sdk/google` guards it with `hasToolCalls`, so a backend that answers `stop` alongside `tool_calls` defeats `finishReason === "tool-calls"` and `finishReason !== "stop"` alike.
- **When the chain is exhausted the user is told what the _last_ link said, not what the most alarming link said.** A static priority table used to rank the reasons and the shown verdict was the argmin over it, so the reason the user read had no relation to where the run actually died: two links failing on a broken key (`auth`, rank 1) ahead of a last link out of quota (`rate-limit`, rank 3) produced "the review service is temporarily unavailable" for a run whose truth was "every provider is out of quota, retry in about a minute" — reproduced in production, where the log line carried `reason: "rate-limit", shownReason: "auth"`. The rule is now `verdicts.at(-1)` with exactly one caveat: an `unknown` last verdict yields to the most recent concrete one, because "we could not classify this" is never more informative than a diagnosis another link already made. The caveat stops there on purpose — `server` does **not** yield, because "the upstream answered 5xx" is an honest diagnosis of the link that actually ended the run, and letting it step aside for an earlier `context-overflow` would tell the user their PR is too large when a provider simply fell over. Two shapes are outside the rule by construction: the BYO chain is a single candidate, and an `aborted` failure does not hop, so it ends the run at its own link and is never aggregated with anything.
- **A failure reason names the event, not the size of the pull request.** One `too-large` used to stand for four unrelated events; they are now `context-overflow` (the input exceeded the model's window), `provider-limit` (the per-minute token bucket refused the request), `output-truncated` (`finishReason: "length"`) and `steps-exhausted` (the step ceiling ended the loop). The split is not cosmetic: only `context-overflow` reaches the user under the "This PR is too large to review" card, the two cut-short reasons say the review was cut short, and the failover divider labels all four differently, so a hop can no longer claim a provider "ran out of context" when it ran out of steps.
- **Statuses are read before message markers, because a status is evidence and a substring is a guess.** Groq answers a per-minute-budget refusal with **413** and a body that reads «Request too large … on tokens per minute (TPM): Limit 8000, Requested 8078», so 413 means `provider-limit` here and never "oversized input"; 429 and 529 likewise decide on their own. The context-overflow markers now only judge what no status claimed — typically a 400 — and the loosest of them was narrowed from a bare `too long` to `prompt is too long`/`messages are too long`, which is the wording Anthropic actually sends; `context length`/`context window` stayed as they were.
- **Every refusal names the card it wants instead of letting the client guess.** Every pre-stream refusal carries `x-review-error` — the two hand-built responses that always did, plus the ones from `errorToResponse` (previously a body and a status and nothing else), the rate-limiter refusal, and the 415/400 input rejections — and a failure inside the stream is preceded by a terminal `data-errorKind` part. The kind travels _beside_ the error rather than inside it because the SDK's error chunk is fixed to `{type:"error", errorText}` (`node_modules/ai/dist/index.mjs:8359-8380`), and matching on the message text would break the moment a message is reworded. The client keeps its status-based fallback for responses that carry no header. GitHub's 502 gets its own `github` kind rather than reusing `load` (which would hide "Try again" on a transient upstream blip) or `review` (which would print a Request ID for a review that never started).
- **"Try again" is offered only where a retry can plausibly succeed, and our quota is not the providers' quota.** The `rate-limit` kind now covers only the counters that answer with a stated reset — our own 25/hour and 8/hour limiters, and GitHub's — and it joined the non-retryable kinds, because the card already states the wait and every click of that button used to consume a slot of the request limiter, hit the review limiter and return the same 429: the user could shorten nothing and lengthen their own wait. A provider running dry is the opposite case and gets its own `provider-quota` kind: the free chain shares per-minute budgets, all three links can be empty at the same moment, and a retry a minute later genuinely goes through (the production run that motivated this did exactly that), so the button stays. Folding the two into one kind would have made the card contradict itself — "try again in a moment" printed above no way to try. The trade-off left in place is that the request limiter's own 429, where the wait can be short, hides the button too; "Edit URL" returns to the form, and a countdown that re-enables the button when `retry-after` expires is UI work deferred rather than a missing piece of this rule.
- **The review limiter is consumed before GitHub is called, not after.** It used to sit behind `getPRMetadata()` and `getPRFiles()`, so a request that was going to be refused anyway still spent two GitHub API calls first. The price of the swap is that a refusal which never reaches a model — a private PR without a token, a PR over the file cap — now costs a review slot; that is accepted because both are user-visible, immediately actionable mistakes, while the ordering it replaced charged the shared GitHub budget for every doomed retry. URL parsing stays ahead of the limiter: it is local, and a typo should not cost a slot. The limiter's Lua script still consumes only on the allowed path, which is what makes the refusal itself free.
- **A candidate that cannot fit the transcript is skipped before the request is sent, not after it is refused.** Before every `streamText` call — including the first — the orchestrator estimates the request at `JSON.stringify(streamMessages).length / 3.5`, plus a fixed overhead computed once from the real strings (the `SYSTEM` prompt plus the JSON of all six tool schemas _with_ their descriptions, which ride along on every step: ~2 850 characters of prompt and ~7 600 of schema, about 3 000 tokens), plus the candidate's own `maxOutputTokens`, because Groq and Cerebras reserve the declared ceiling at admission (§4). Over 80 % of `tpmBudget` the candidate is skipped with a `data-failover` divider of its own, `over-budget` — zero requests spent, zero retries slept through, and a divider that says something different from the provider's own 413. The reason is deliberately distinct from `provider-limit`: one is our prediction, the other is the provider's verdict. On the closing link the same check ends the run under the `provider-quota` card with a message about the review's size rather than the PR's, since a `context-overflow` card would blame the wrong thing — 6 400 admissible tokens on Groq is a budget problem, not a 131k context problem. The estimate is deliberately conservative in one direction only: JSON escaping and 3.5 characters per token both overstate, and overstating costs a hop while understating costs a doomed request. Mid-attempt enforcement through `stopWhen` was considered and rejected — the entry check already prevents the expensive case, and folding a budget clause into `stopWhen` would entangle it with the exhaustion discriminator above, which reads the _shape_ of the last step and must stay readable.
- **A successor resumes its own interrupted review, and is told exactly where that review stopped.** Handing a model 40k tokens of a transcript it did not produce gave, twice out of two observations, a verdict in five seconds with zero tool calls of its own: the inherited notes look like a finished investigation, and on the error branch the transcript even ends on a `role: "tool"` message (`node_modules/ai/dist/index.mjs:3942-4050`), i.e. the normal "results are in, conclude" state. Two mechanisms answer that, each on its own condition, stated in the bullets below: a synthetic `user` message appended after `sanitizeForHandoff` at **both** insertion points — the cut-short hop and the error hop, the cut-short branch being if anything the more misleading of the two — whenever there is a review to resume at all, and, while that review still has diffs left to read, `prepareStep` returning `toolChoice: "required"` with `activeTools` reduced to the five reading tools on step 0 (`node_modules/ai/dist/index.d.ts:986-1023`), so that the only move available is a read: `toolChoice: "required"` alone would let the model satisfy the requirement by fabricating an `emit_issue`. Neither condition is "index > 0", because a budget pre-flight skip advances the index without handing anything over.
- **The nudge speaks in the first person, because the transcript above it is the model's own.** Its first version spoke of a third party — "the reviewer that wrote the notes above was interrupted", "treat any issue the previous reviewer reported as a claim to confirm" — while `inherit()` splices those steps in as the new model's _own_ assistant turns, which is the only thing chat-completions history can express. The contradiction was resolved by the model, not by us: after a double failover, `gemini-2.5-flash` concluded that the transcript was its own, that there was therefore no separate prior report, and that it was consequently the first reviewer — skipped every remaining file and closed with the literal `No issues found.` while two real issues had already been emitted, enriched, streamed and stored. The issues survived; only the closing narrative lied, which is the worse half to get wrong, because that sentence is what the reader takes as the verdict. So the nudge now says the review _above_ was interrupted mid-way, that the work already done stands, and that it must be resumed — never mentioning engines, providers or a previous reviewer, since none of that is visible or actionable to the model being asked to continue.
- **The nudge carries the state of the review, not an instruction to rediscover it.** `buildHandoffNudge` (`lib/review/system-prompt.ts`) is given three facts computed at handoff time: the issues already emitted, rendered as severity plus `file:line` from the live `UIIssues` map; the diffs already **requested**, collected by scanning every accumulated message for a `get_diff` tool call, taking its `filename`, intersecting that with the PR's own file list and deduping in first-seen order; and the diffs not yet requested, which is the PR's file list minus the first set **minus everything flagged `generated`** — the SYSTEM prompt tells the model to skip build output, and a nudge that then names `dist/…` as homework would contradict it. "Requested" rather than "read" is the whole claim the counter can support: it counts calls, not answers, and it counts one per file rather than one per part, so a file refused as `no_patch` or cut off at `part_limit`, or read as one part out of five, still lands in that list — the words were aligned with the counter instead of the counter being upgraded to match the words. The two lists and the `file` of each issue are author-controlled strings — after the intersection nothing model-invented reaches an interpolation site — so every interpolated name has its runs of control characters and Unicode line separators collapsed to a single space at the formatting boundary, where the guarantee holds for any caller: git permits a newline in a path, and the nudge is a `role: "user"` message — the one channel SYSTEM tells the model to trust — so an unsanitized path could forge a state line or an instruction inside it. The exception mirrors SYSTEM's own ("read one only if the PR changes nothing else"): when every file in the PR is generated, the generated files _are_ the reviewable set, because the alternative is a first handoff that reports nothing requested, nothing left to request and "finish the review now" — a verdict on a PR the model never opened, which is the failure this whole section exists to prevent. Two shapes come out of that. With files still unrequested, the nudge ends "read each remaining diff with `get_diff` … if `get_diff` refuses a file, follow the refusal's guidance instead of retrying … your next action must be a tool call" — the refusal payloads already carry per-scope guidance (§4), and naming a file as outstanding is otherwise an invitation to retry it. With nothing left to request it ends "emit any issue you have found but not yet emitted, then close", and — only when issues exist — states the closing line outright. The re-verification clause that used to sit here ("treat any issue as a claim to confirm", "read every file you have not read yourself") was deleted rather than reworded: there is no retract path, an emitted issue is enriched, streamed and saved regardless of what a later step thinks of it, so the instruction bought nothing and cost a full second reading of a PR whose budget was already spent once.
- **The closing phrase binds to the conversation, not to the current model's memory of it.** The two SYSTEM rules used to read "if you called `emit_issue` at least once" and "if you found no issues" — first person, present tense, and therefore trivially satisfiable by a model that has decided the steps above are not its own. They now key on whether an `emit_issue` call exists **anywhere in this conversation, including steps before an interruption**, and the no-issues branch adds "do not call `emit_issue` just to have one" so the repair cannot run the other way. The phrases themselves — `Review complete.` and `No issues found.` — are untouched; they are the established contract with the UI and with anyone reading a stored review.
- **Only one nudge is ever in the array, and it is always the current one.** A nudge states facts as of the moment it was written, so after a second failover the first one is a lie sitting in the middle of the transcript, telling the model that files it has since read are still unread. `inherit()` therefore tracks the index of the message it appended and splices it out before pushing the next segment and a freshly computed nudge. The consequence is that two inherited segments now sit adjacent with no user turn between them; nothing re-validates role alternation on the way out — the OpenAI-compatible providers accept consecutive assistant messages, and the Google converter maps each assistant message to its own `model` turn without merging or checking (`@ai-sdk/google/dist/index.mjs:571-575`). The `prepareStep` forcing is gated on the same state: it applies only when the last handoff left files unread, because `READING_TOOL_NAMES` excludes `emit_issue`, and forcing a read on the branch whose whole instruction is "emit what you have and close" would make the two contradict each other. A candidate that fails before its first step hands over an empty segment; when there is also no earlier handoff there is nothing to resume, and no nudge is appended at all.
- **Two repairs were considered and rejected.** Rewriting the model's closing sentence server-side when the issue count disagrees with it fabricates output attributed to a model that did not write it, which is the same failure as the one being fixed, only ours. Logging a warning on the mismatch was rejected as recording a defect it cannot fix — the user still reads `No issues found.` above two issues. Rejecting a verdict and re-prompting until N steps have passed was rejected earlier for its own reasons: it doubles latency on the slowest link and a stubborn model just burns the counter with junk calls.
- **A hallucinated tool name is not a failure mode, and the SDK is what makes that true.** An unknown tool name never escapes `parseToolCall`: the `NoSuchToolError` is caught and returned as a call marked `invalid` (`node_modules/ai/dist/index.mjs:3761-3777`), converted to a `tool-error` part (`:6340-6352`) that counts as a fulfilled client tool output (`:7618-7623`), and fed back to the model as a `role: "tool"` message carrying the error text (`:4042-4058`) — so the loop runs another step and the model corrects itself. `onError` does not fire, because that path emits `tool-error` and not `error` (`:6718-6720`). This was verified against a mock model as well as by reading: two `doStream` calls, recovery on step 1. It matters because the exhaustion discriminator above would misread an early exit with an unanswered tool call as a success, and this is the scenario that looked most likely to produce one. The paths that genuinely can exit below the ceiling holding an unanswered client call are a tool with no `execute` and a tool awaiting approval (`:6366-6380`); we have neither, and a throw _inside_ `execute` is also converted to `tool-error` and continues (`:2907-2928`).
- **Text that came from upstream is trimmed at the boundary with the user, not at its source.** Octokit returns the whole response body as the message when the body is not JSON (`@octokit/request/dist-src/fetch-wrapper.js:133-136`), so a 502 from GitHub's edge used to render an entire HTML document inside the error card. The trim (collapse whitespace, 240 characters, ellipsis) lives in the formatter that builds the user-facing message, so the untouched `e.message` still reaches the model as a tool `reason`, where the detail is what makes the hint actionable.
- **Every GitHub call carries the request's abort signal and a 15-second timeout, and the timeout had to be built rather than configured.** `request.timeout` is documented-looking and completely inert in Octokit v22: `fetchWrapper` enumerates the six `request` keys it forwards and `timeout` is not among them (`node_modules/@octokit/request/dist-bundle/index.js:52-61`), while `RequestRequestOptions`' `[option: string]: any` index signature lets it compile — a grep for `timeout` across all of `@octokit/*` finds it only in unrelated OpenAPI response schemas. The working seam is `request.fetch`, which the same wrapper does honour, so the client is built with a fetch that composes the caller's signal with a per-request timer (`lib/github/octokit/timeboxed-fetch.ts`); a constructor-level `request.signal` could not do this, because a single timeout signal would expire once for the whole client. As on the provider side, the timer is cleared the moment the headers resolve and therefore bounds the first byte only — a declarative `AbortSignal.timeout` would still be armed while the body streams, and Octokit swallows a body-read failure into an empty string (`getResponseData`), which surfaces later as `GitHubApiError(200, "Expected file …, got undefined")`: a misleading cause instead of an honest timeout. Past the headers the backstop is undici's 300-second `bodyTimeout`, the same as for providers. The caller's signal stays composed in for the whole request, so a Stop still aborts a body in flight; it is now threaded from `runReview` into `createGithubAccess`, so pressing Stop kills in-flight GitHub work instead of leaving it running against a browser tab that is already gone.
- **A GitHub timeout is a distinct error class, because the status it arrives with is a lie.** The timer aborts with an explicit `TimeoutError` reason — the same name a native `AbortSignal.timeout` or undici would produce, shared as one constant between the fetch that raises it and the classifier that reads it — and a `TimeoutError` does not take Octokit's `AbortError` fast path and is therefore wrapped in `RequestError(message, 500)` (`node_modules/@octokit/request/dist-bundle/index.js:62-83`) — and `isRetryable` is `status >= 500`, so a timeout used to buy three attempts of 15 seconds each. `translateOctokitError` now reads the `cause` before the status and raises `GitHubTimeoutError`, which is a sibling of `GitHubApiError` rather than a subclass, so it falls out of the retryable class by _type_ rather than by a carve-out on a status number that GitHub's edge legitimately returns. A user abort needs no such handling: Octokit rethrows an `AbortError` raw with a `status = 500` bolted on and no `RequestError` wrapper, so it never reaches the 5xx branch — but `withRetry` checks the signal before each attempt and before each sleep anyway, and its backoff sleep is now abortable, so nothing survives Stop by a full backoff.
- **Tools return every GitHub failure as a soft status, and the price is that quota exhaustion is invisible to the orchestrator.** `get_file_contents` and `list_directory` used to catch two of the six error classes, so an exhausted rate limit, a revoked token or a timeout left `execute` as a raw throw; the SDK turns that into a `tool-error` and continues the loop (`node_modules/ai/dist/index.mjs:2907-2928`) without ever setting `failure`, so the run neither hopped nor stopped — it just kept reading with a broken client. Both catches now widen to `GitHubError` and answer `{status: "unavailable", reason}`, keeping the `NotFoundError` branch above it because "this file does not exist" is a different fact from "we could not read it". The known limitation this creates is deliberate: a soft status is invisible to `runReview`, so an exhausted GitHub quota can never trigger a provider swipe — and it should not, since swapping models does not refill GitHub's bucket. What it costs is that the model, not the orchestrator, decides what to do about it; `system-prompt.ts` already forbids a verdict when every read failed, which is the guard that matters. A separate channel from tools up to the chain is not built.
- **An issue about a path this PR does not touch is refused rather than published.** `emit_issue` validated `file` as a non-empty string and went straight to `enrichIssue`, which fetched no patch for an invented path, produced no code lines, and still built a `blobUrl` out of it — so a hallucinated location reached the UI and the database as a normal card whose GitHub link 404s, while the model was told `{ok: true}` and had no reason to correct itself. The check is `gh.getFile(input.file)` against the already-loaded map, zero requests, and it returns the file's _current_ path rather than a yes/no: a renamed file is accepted under its `previousFilename`, but the issue is then anchored to the name the map is keyed by, because passing the old path on to `enrichIssue` would find no patch, produce no code lines and build a `blobUrl` that 404s — the very failure the check exists to prevent. Re-anchoring also makes the two names collapse into one issue id, so the same finding reported under both is a duplicate rather than two cards. `patchFound` could not have served here: GitHub legitimately serves no patch for binaries and very large files, so "no diff" is not evidence of "not in this PR". The refusal is a `not_in_pr` status whose text sends the model to `get_pr_files_summary` and says outright that resending the same path will fail again — an instruction to retry is exactly what turns one bad guess into a loop.
- **A patch read only in part is visible to the reader, not only to the model.** Truncation used to exist solely in the tool's answer: `patch_truncated` appeared twice in the codebase, both times in `review-tools.ts`, and a half-read file rendered in the UI as a completed read. The trace row for `get_diff` now carries `part i/N` next to the filename, and the sidebar marks a file `partial` when the parts it served do not cover `total_parts` — counted as _distinct_ parts seen, so a file re-read three times still reads as incomplete if part 2 was never asked for, and a file whose only `get_diff` came back `part_limit` counts as partial as well, that being the strongest case of a file left unread. Both derive from the tool output already in the transcript (`patchPartOf`, `partiallyReadFiles` in `lib/review/transcript.ts`), so no new stream part was needed; the one addition is that _every_ tool result now refreshes the sidebar's copy of the tool entries, which previously only changed when a new call _started_. Refreshing it just for results that carry part numbers is not enough: a refusal carries none, and the terminal case — the last `get_diff` before the verdict answering `part_limit` — would leave the entry mutated in place with no new array to re-run the memo against, so the file would render as fully read.
- **The file limit counts the files a reviewer would actually read.** The gate used to compare GitHub's raw `changed_files` against `MAX_CHANGED_FILES`, so a lockfile or a `dist/` bundle consumed the same quota as a source file the review exists for — and the product already calls those files noise: `isGeneratedPath` flags them and the prompt tells the model to skip them. The precise check now runs after `gh.getPRFiles()` on `prFiles.filter(f => !f.generated).length`, which costs nothing because the same memoised call is made a few lines later anyway; the price is that a rejection now happens after the file list is fetched rather than before, and a raw `RAW_CHANGED_FILES_CEILING` check on the metadata still stands in front of it so a monstrous PR is refused without paginating `listFiles` at 100 per page. The flag itself is no longer computed only for the model: `ReviewFileSummary` carries it to the sidebar, where a lockfile that the agent walked straight past no longer looks like a file it ignored for no reason.
- **A file too large to serve is refused before it is decoded, and one physical condition now carries one status.** The cap used to be applied a layer above the fetch (`review-tools.ts` compared `size` after the fact), so the body was downloaded, base64-decoded into a string and only then discarded — and the decoded string stayed in `fileContentsCache` for the rest of the request. The cap is now an argument of `getFileContents`, checked against `data.size` before `Buffer.from`, and a refusal is `content: null`, so what the cache holds for a rejected file is a size and a sha. The same branch absorbs GitHub's >1 MB case, which arrives as a 200 with `encoding: "none"` and used to throw a `GitHubApiError` the tool reported as `unavailable`: two thresholds, two statuses and two different pieces of advice for the one fact "this file is too big to hand you". Both are `too_large` now, and `too_large` points at `get_diff`, which — since patches paginate — can genuinely deliver the whole change. The threshold itself moved from 9 000 to 18 000 bytes, because an ordinary 250-line TypeScript file was over the old one, i.e. the tool refused exactly where the surrounding context was worth having.
- **`list_directory` is cached like every other read.** It was the one path to GitHub that went straight to `withRetry` with no map in front of it, so a model that listed the same directory twice spent the quota twice — bounded but pointless, and on the BYO path (`stopWhen: () => false`) not bounded by a step ceiling at all, while the quota being spent is still the server's PAT. It now uses the same shape as `fileContentsCache`: a `Map` keyed by `${ref}:${path}` holding the in-flight promise, with the entry removed when that promise rejects so a transient failure is not cached as a fact.
- **The client is told when a finished-looking review will get no share link, because it cannot work that out itself.** Exhaustion reaches the browser looking positive — the `finish` chunk carries the last step's reason, `stop` or `tool-calls` — so a client keyed on `finishReason` alone would render "Review complete" for a run the server just refused to persist; and a save that was attempted and failed is indistinguishable from one that was never attempted, since both simply produce no `data-share`. Both facts exist only on the server, so the terminal `data-outcome` part states them: `incomplete` drives the cut-short heading, `saveFailed` the "couldn't create a share link" notice. The notice deliberately does not claim the review was not saved, and it stayed that way after the timeout moved to the server (§6): a statement the server cancels leaves no row, but a connection lost after the commit and before the acknowledgement still reads as a failure here, so "there is no link, and a re-run is what produces one" is the strongest claim that is always true. A save that was skipped rather than attempted (private, stopped, mock) says nothing at all.
- **The share page's OG image degrades to the brand card instead of 500ing, and its staleness is bounded by a timer rather than by invalidation.** The route read the database with nothing around it, so an unreachable Postgres threw, Next answered 500, and the crawler got no image at all — while the `BrandCard` branch that exists for a missing row was sitting right there. It is now the `catch` branch too, with a `warn` so the fallback is visible rather than silent. The degradation itself is cacheable where the 500 never was: the fallback is a valid 200, so a database blip that coincides with a crawler visit pins the brand card to that slug until the hour expires — accepted knowingly, since a branded card beats a missing image for that hour either way. The caching half is a deliberate compromise. Metadata image routes are cached by default (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/opengraph-image.md:91-93`) and an absent `revalidate` means `INFINITE_CACHE` (`server/route-modules/app-route/module.js:237-241`), so the image could outlive its page forever; the previous ceiling of 24 hours made that finite, and it is now **one hour**. The obvious alternative — keep a long window and invalidate on write — was checked against the source and rejected on two independent grounds. `revalidatePath('/r/<slug>')` emits exactly one implicit tag and tags are matched by exact map lookup (`server/web/spec-extension/revalidate.js:85-93`, `server/lib/incremental-cache/tags-manifest.external.js:27-30`), while the OG route is a _separate_ cache entry keyed `/r/<slug>/opengraph-image` (`lib/metadata/get-metadata-route.js:109-113`) — the page path simply does not cover the image. And the write happens inside the stream's `execute`, whereas a route handler flushes its pending revalidations once, right after it resolves its `Response` and before the body streams (`server/route-modules/app-route/module.js:494`), so a call from there is either a silent no-op or an `E263` invariant throw. Doing it properly would mean `after()` with both paths spelled out; one hour of staleness is not worth that machinery, especially since the image can only go stale when the _same_ `headSha` is reviewed twice — a different sha is a different slug and therefore a different cache entry.

## 6. Configuration and environment

- **Everything that changes between deployments** (secrets, keys, hosts, flags) goes through environment variables, not code.
- **The environment is validated at startup** with a typed schema, fail-fast: a missing or invalid value crashes the app immediately with a clear error instead of failing later, mid-operation.
- **`env` is a lying type when parsing fails, and the preload is what makes the lie unreachable.** `lib/env.ts` collapses to `{}` on any validation error while `as z.infer<…>` still tells TypeScript every field is present, so a module that read `env.X` at module scope ahead of `assertEnv()` would get `undefined` with no compile error and no crash. Nothing does today — the container preloads `validate-startup.mjs`, and `next dev`/`next start` reach `register` before the first request — so the guard is the preload rather than the type, and a future module-scope read is the thing to watch for.
- **No external dependency is introduced for configuration** while a hand-written solution covers the need.
- **The client IP comes from the proxy only where a proxy is trusted.** With `TRUST_PROXY=1` the limiter takes the rightmost `X-Forwarded-For` entry — the one the trusted edge appended, so a client-supplied header cannot spoof it — and every deployment behind Traefik/Coolify must set it. Left empty (the local-dev default) all requests are counted under a single `"dev"` bucket, i.e. one shared quota for the whole internet, so an unset value in production is a misconfiguration rather than a safe default; a typo such as `TRUST_PROXY=true` is rejected at startup by the `z.enum(["1","0",""])` schema instead of silently degrading. The third state is fail-closed rather than a hole: with `TRUST_PROXY=1` and no `X-Forwarded-For` at all the request lands in one shared `"unknown"` bucket, which a real user behind Traefik cannot reach — the proxy always appends the peer address — so what stays worth stating is the configuration risk, since `TRUST_PROXY=1` on a container that is _also_ reachable directly puts every direct visitor into that single bucket.
- **The per-IP rate limiter fails open.** If Redis is unavailable, or the check errors or times out, the request is allowed rather than blocked — availability of the review flow is deliberately prioritized over rate limiting during a Redis outage. The connection is awaited with a bounded timeout so a healthy-but-not-yet-connected Redis is used rather than bypassed for the first, sequential request; concurrent requests arriving during the brief sub-second cold-start connect window can still fail open before the first connection resolves — a bounded window that occurs at most once per process and is consistent with the deliberate fail-open, not a fully-eliminated bypass. Failures are logged rather than swallowed so the open state stays visible.
- **Every Postgres statement is bounded by the server, not by a race in the caller.** `saveReview` used to run its insert against a 2-second `Promise.race`, which bounded nothing that mattered: postgres-js 3.4.9 has no `AbortSignal` and drizzle hands out a thenable rather than the `Query`, so losing the race left the statement running and committing — the user was told there was no share link while the row was already in the table, and the slug being deterministic meant the URL was live. `getReview` had no bound at all, and nothing above it supplies one, since the share page is dynamic and `maxDuration` is a serverless concept. The budget now sits on the pool: `connect_timeout: 5` plus `connection: { statement_timeout: 2000 }`, which postgres-js merges into the startup packet (`node_modules/postgres/src/index.js:484-488`, written at `connection.js:996-1006`), so it is Postgres that enforces it. The two numbers bound different phases and each is observable on its own: `connect_timeout` bounds a socket stuck in `connecting`, and therefore how long a dead connection holds one of ten pool slots and how late the reconnect starts; `statement_timeout` bounds every query once the connection is ready. Three consequences are deliberate. The parameter is session-wide, so the same 2 seconds cover `getReview` and the readiness probe's `select 1`. A cancelled insert now surfaces as `57014 query_canceled` under the `saveReview failed` log line — a louder message for what used to be a silent success. And 2 seconds is chosen against a Postgres container on the same docker network, where a round trip is tens of milliseconds; if the database ever moves behind a network, this number is the one to revisit.
- **An upsert rewrites the whole row, so `created_at` is a misnomer that is kept on purpose.** Re-running the same `headSha` hits `onConflictDoUpdate` and replaces the title, the issues and the model id, so what the share page shows is always the latest run — printing the _first_ run's date next to it would be a lie about the content underneath. The column therefore behaves as `updated_at` and is named `created_at`; the name is left alone not because the rename would be expensive — the `model_id` rename below paid exactly that price — but because here it would buy a label the UI never prints: the page shows a bare date after `head <sha>` with no "created" beside it, so the misnomer misleads only a reader of the schema, and this bullet is that reader's correction. `owner` and `repo` _are_ in the conflict `set`, unlike the rest of the identity: the slug hashes a lower-cased canonical string (`lib/db/slug.ts`) while `parsePRUrl` keeps the URL's original case, so `…/Vercel/Next.js/pull/123` and `…/vercel/next.js/pull/123` are one row, and without them in the `set` that row would display the casing of whoever ran it first forever.
- **A row holds the verdict and nothing that produced it, and nothing expires it on purpose.** What is written is the PR identity (`owner`, `repo`, `pr_number`, `head_sha`), the PR title, the model id and the issues the model emitted, each carrying the few diff lines it points at. The diff itself, the file contents, the prompt and any token a user brought never reach the database, the client IP lives only in the rate-limiter keys in Redis, which expire with their own windows, and in the request log lines §7 describes, and a private review is not saved at all, which is the same guarantee §7 defends on the logging side. There is no TTL, no retention job and no index beyond the primary key, because the only read in the codebase is `getReview(slug)`, an exact primary-key lookup: nothing selects by owner, date or model, and an index no query uses is a cost paid on every insert. Growth is bounded by the limiter the product already advertises — 8 reviews an hour and 10 a day per address, a row of a few kilobytes, and an upsert that replaces the row rather than adding one when the same `head_sha` is reviewed again — which puts this table in the megabytes a year at the traffic a portfolio artefact sees. If that ever stops being true, deleting by `created_at` is the migration to write, and it needs an index this schema deliberately does not carry yet.
- **Database migrations run in the container entrypoint, serialized by a session-level advisory lock.** The entrypoint applies pending Drizzle migrations before it starts the server. To stop two replicas — or two overlapping zero-downtime deploys — from racing the same non-idempotent DDL (`CREATE TABLE "reviews"` has no `IF NOT EXISTS`), `migrate()` is wrapped in a blocking `pg_advisory_lock(MIGRATION_LOCK_KEY)` taken on the shared `max: 1` postgres-js connection: one physical connection means the session-level lock covers both the `__drizzle_migrations` read and the DDL, so `sql.reserve()` is unnecessary. The loser blocks until the winner releases, then re-reads the migration journal and applies nothing — idempotency comes for free. The key is a fixed integer constant, sent as an untyped parameter that resolves to the sole single-argument `pg_advisory_lock(bigint)` overload by arity. The trade-off is deliberate: migrate-in-entrypoint plus an advisory lock, rather than a one-shot pre-deploy migration job — it is simpler, lives entirely in the repository, and holds up under scale-out. The unlock in the inner `finally` swallows its own failure, because it is a real query: a migration that failed on a dropped connection would fail the `pg_advisory_unlock` too, and the second error would replace the first before anything caught it — the operator would read a connection error where the truth was a broken DDL. Nothing is lost by swallowing it, since a session-level lock is released when the connection closes a few lines later. `sql.end()` in the outer `finally` needs no such guard: it is a race between a destroy timer and `Promise.all` over the connections, and neither side can reject (`node_modules/postgres/src/index.js:365-375`).
- **The migrator reads `process.env.DATABASE_URL` raw, and it is the one deliberate exception to the typed validation this section opens with.** `migrate.mts` is a separate esbuild bundle that runs before the application in the same entrypoint, while `EnvSchema` is all-or-nothing: importing `lib/env` would make a migration demand `GITHUB_PAT`, three provider keys and `REDIS_URL`, none of which it uses, so a perfectly reachable database could not be migrated because a model key was blank. Fail-fast is not given up — a missing URL throws before the first connection is opened — and the full typed validation runs seconds later in the same entrypoint, in the `--import ./validate-startup.mjs` preload.
- **`drizzle.config.ts` deliberately carries no `dbCredentials`, so `push`, `studio` and `pull` fail loudly.** drizzle-kit 0.31.10 puts those three through a connection-parameter check and exits non-zero without it; none of them is wired into `package.json`, where the only Drizzle entry points are `db:generate` (which writes a migration file) and `db:migrate` (the migrator above). `push` is the one whose absence is worth having: it applies the schema directly _without_ producing a file, after which `drizzle/meta/_journal.json` disagrees with the database — and the journal is exactly what `migrate()` reads to decide what is pending. A loud, self-describing refusal is a better default here than the convenience.
- **The model id lives in a column called `model_id`, and getting there cost a deliberate incompatibility window.** The column was created as `provider` while what `saveReview` writes has always been `candidates[i].modelId`, so the name asserted something the data never supported (§4). The fix is one `ALTER TABLE … RENAME COLUMN` (`drizzle/0001_exotic_snowbird.sql`) rather than the add–copy–switch–drop dance, and the price is that during a deploy the old image is briefly talking to the new column: the entrypoint migrates before it binds the port, so between the rename and the new server accepting traffic the _previous_ container is still serving `/r/<slug>` and its `select` names a column that no longer exists — every share page 500s for those few seconds. That is accepted rather than engineered around: this is a single low-traffic container, the affected surface is read-only share pages, and a four-step migration to protect a few seconds of one deploy is a worse trade than the window.
- **`/api/health/ready` exists, is wired to nothing, and is kept as the point a probe would attach to.** The container's `HEALTHCHECK` calls `/api/health/live`, which answers 200 unconditionally, and Coolify's own health check is configured in its UI rather than in this repository — so nothing in the tree references the readiness route. It stays because it is the only place that actually asks whether Postgres and Redis answer, which is what a deployment probe should be asking; pointing Coolify at it is a configuration change and no code. What it does now that it did not before is say _what_ failed: `Promise.allSettled` collects both checks, and every rejected one is logged with its name and its error before the 503 goes out. Previously an operator saw a bare status and could not tell Postgres from Redis. The 2-second bound per check is the same budget the pool enforces on the `select 1` anyway, and reaching it against a container on the same network means the database is genuinely overloaded — which is exactly when a readiness probe should fail. The `withTimeout` helper the route shares with `validate-startup.ts` now lives in `lib/with-timeout.ts`: it was a verbatim copy in two places, one of them in `app/` against §1. That module has to stay dependency-free — `validate-startup.ts` is bundled by esbuild and runs before the app, so pulling `server-only` or `lib/env` into it would break the preload.
- **The container is deliberately allowed to look `unhealthy` while it migrates.** `--start-period=30s` plus `--retries=3` × `--interval=10s` gives roughly 60 seconds before the mark, and the entrypoint runs migrations before it binds the port, so the probe does fail for that whole stretch. The mark is informational here rather than actionable: outside Swarm, Docker does nothing with `unhealthy`, and this deployment is a single Coolify-managed container. The one realistic path past 60 seconds is a deploy blocking on the `pg_advisory_lock` above while an overlapping deploy holds it — a case already accepted as deliberate — and widening the budget to 120s would only trade it for a genuinely broken container sitting in `starting` for two minutes. The budget stays at 30s.
- **The base image stays on the floating `node:26-slim` tag, with no digest pin.** Pinning a digest is only worth it together with automated base-image updates: without Renovate or Dependabot it freezes the base image _and its CVEs_, which is a false sense of security rather than a supply-chain control. The price accepted instead is that builds are not bit-reproducible — "green yesterday" does not guarantee "green today" at unchanged code. Revisit the pin only if automated updates land.
- **CI builds the image once and pushes exactly what it smoke-tested.** A single `build-push-action` with `load: true` carries the `metadata-action` tags and labels, the smoke tests run against that loaded image, and a plain `docker push` then ships those same tags. The previous shape built twice — once to load, once to push — and while the file layers were identical, the pushed config blob differed by tags and OCI labels, so the object in the registry was never literally the object that was tested. This closes off the path to multi-arch images, which is accepted: production is one amd64 VPS.
- **The smoke test runs in two phases, because a single phase could only ever prove the migration guard.** With no environment at all the entrypoint short-circuits at `node migrate.mjs`, so `--import ./validate-startup.mjs` never loads and no breakage of the preload could fail the test. Phase one keeps that check and asserts the migration's own message; phase two hands the container a real Postgres and no model keys, so the migration applies and the preload is what fails — asserted on the `validate-startup.mjs` frame in stderr, which the `instrumentation.ts` second net cannot produce. Phase two runs detached behind a bounded wait: with the preload wired out of the entrypoint Next does not crash, it retries the instrumentation hook indefinitely, so a blocking `docker run` would hang the job rather than fail it. The workflow guard is `grep -q -- '--import ./validate-startup.mjs' Dockerfile`; the bare `validate-startup.mjs` it replaced also matched the `COPY` line and passed even with the flag deleted from the entrypoint.
- **PID 1 in the container is `tini`, not the shell.** The entrypoint is `tini -g -- sh -c "node migrate.mjs && exec node … server.js"`, so `tini` reaps zombies and forwards signals to the child's entire process group (`-g`). Without it, during the migrate phase the intermediate `sh` is PID 1 and swallows `SIGTERM` — the `exec` that hands PID 1 to the server only happens on the second half — so a `docker stop` or redeploy mid-migration would hang until `SIGKILL`. Group-mode signalling reaches `node migrate.mjs` directly, so shutdown during a migration terminates cleanly instead.

## 7. Observability and security headers

- **Structured logs in the review flow go to stdout as JSON** through a single `pino` logger (`lib/log.ts`, behind the `server-only` barrier) — no extra env var: the switch is `NODE_ENV` alone, production writing raw JSON with no transport while development pipes the same records through `pino-pretty` (a devDependency) purely for readability. Errors are passed as raw objects at the call sites and sanitized centrally by a custom `err` serializer that wraps `pino`'s standard one: it strips the AI SDK's `requestBodyValues` (the full prompt — the private diff and file contents) and `responseBody` recursively (top level, the `aggregateErrors` array and any nested error/`cause` object) while keeping type, message, stack, status and the cause chain. Without this, a routine provider 429/529 during a private-PR failover would write the private code to stdout (which Coolify persists), breaking the "private reviews aren't persisted" guarantee. The same walk drops seven auth header names — `authorization`, `proxy-authorization`, `cookie`, `set-cookie`, `api-key`, `x-api-key`, `x-goog-api-key` — matched case-insensitively on the key at any depth rather than at a fixed path, because the header bags that reach the serializer arrive in different places (`responseHeaders` on an AI SDK `APICallError`, `request.headers` and `response.headers` on an Octokit `RequestError`) and each library redacts, or does not redact, on its own terms. The Redis client and the rate limiter log through that same instance as `component`-tagged child loggers, so a Redis socket failure or a fail-open rate-limit check arrives as JSON on stdout next to the review flow instead of flat `util.inspect` text on stderr. A 30-second per-signature window in `lib/redis.ts` collapses a flapping connection into one line plus a `suppressed` count. The Coolify container captures both stdout and stderr and owns aggregation.
- **Every review carries a `requestId`,** threaded as a `pino` child logger through the orchestrator and into the model tools, so a request's failover, DB-save and enrichment logs correlate under one id. The id now exists end to end rather than in the logs alone: the browser mints it, sends it as `X-Request-Id`, and shows it on the error card, the route accepts it **only if it parses as a UUID** and otherwise mints its own — an arbitrary client string must never become a log field or an echoed response header — and `onRequestError` in `instrumentation.ts` reads that same header through the same validator (`lib/request-id.ts`, one pattern for both entry points; the Node header type also admits `string[]`, which is not an id and becomes `undefined`), so an error that escapes the route is filed under the id the user is looking at and nothing else gets in. Feature detection guards the client side: `crypto.randomUUID` is absent outside secure contexts, and there the header is simply omitted.
- **The route's call into the orchestrator is wrapped, because an unexpected throw used to erase the id.** `res.headers.set("x-request-id", …)` ran only on a normal return, so any exception that was not a `GitHubError` — a `TypeError` on a PR whose base repository was deleted (GitHub answers 200 with `repo: null`), a raw `AbortError` from Octokit's fetch wrapper, a throw out of `selectModels` — produced a bare Next 500: empty body, no id, and a card reading "Review failed" with nothing to quote. The `catch` logs explicitly before answering (swallowing the exception would otherwise hide it from `onRequestError`) and returns 500 with both `x-request-id` and `x-review-error`.
- **A throw out of the stream's `execute` leaves a log line, not just a card.** `createUIMessageStream` uses `onError` purely as a text formatter (`node_modules/ai/dist/index.mjs:8359-8380`), so passing it the message builder meant the one realistic throw — `toUIMessageStream`'s `default: throw new Error("Unknown chunk type: …")` on a part the SDK version does not know (`:8117-8120`) — reached the user and no one else. It now logs and then formats.
- **The previously silent failure sites now leave a trace:** a failed `saveReview` (the share link silently never appears), provider failover and final exhaustion, and an enrichment snippet that couldn't be built.
- **A run ends in one of three terminal events, and they are not interchangeable:** `review finished` carries the slug and is written only when the review is actually in the database; `review not saved` carries the reason it is not (`private`, `aborted`, `truncated`, `mock`, `save-failed`); `review failed after providers exhausted` covers the runs that ended on an error. The first two carry the same context — provider, model id, issue count, `finishReason`, step count, duration — so a run stopped at the step ceiling is distinguishable from one that hit the output limit without reading the message string. One path leaves no terminal line at all, and it is a known gap rather than a design: an abort that surfaces as a classified `aborted` failure returns silently. Previously `review finished` was written for every run that did not throw, including the ones that were deliberately never persisted.
- **Every model step logs its token usage** — input, output, reasoning and total — next to its step number, the provider, the model id and the ceiling that step ran under. The UI only ever sees the running total, so without this line the output ceilings would stay guesses; the log is what turns them into a per-step distribution the numbers can be revisited against. It is emitted at `info` deliberately: production runs `pino` at `info`, and a `debug` line would never be collected where the data actually accumulates.
- **Every request to a provider leaves a line, so a retry is no longer invisible in both the UI and the logs at once.** The custom `fetch` of §4 writes provider, host, status, `retry-after` and duration for each attempt, and a `warn` for each attempt that threw, distinguishing a TTFB timeout from a transport failure. Before this, the only provider-shaped records were "model attempt started", "provider failover" and the terminal line, all of them per _candidate_: a link that answered 429 twice and succeeded on the third try was indistinguishable in the logs from one that answered on the first. Bodies are never logged — the private diff travels in them, which is the same reason the `err` serializer strips `responseBody`.
- **The budget estimate is logged next to the usage it is trying to predict.** "model attempt started" now carries `inputEstimate`, the candidate's `budget` and its `maxRetries`, and the very next "model step usage" line for that candidate carries the provider's own `inputTokens` for step 0. The pair is what makes the 3.5-characters-per-token divisor and the fixed schema overhead falsifiable against production traffic rather than against a guess; a pre-flight skip writes `estimate` and `budget` on its own `warn` line instead. The client-side heartbeat is the same idea aimed at the user: the browser stamps the arrival of every _network_ chunk (right after `reader.read()`, deliberately upstream of the reveal throttle, which paces already-received text) and says so on screen after eight seconds of silence and again after thirty, because the provider pause it covers can legitimately last a minute and the UI had nothing moving but a CSS spinner and a seconds counter.
- **The reveal throttle paces text and nothing else: events are not queued behind it.** `revealTranscript` walks the whole ledger against a character budget, and the entry that overruns it used to end the walk — so a `tool` row or a provider-switch divider standing _after_ an unfinished paragraph waited for that paragraph to finish typing, while `setIssues` and `setToolEntries` bypass the throttle entirely. The observable result was a console whose header said "call 2" and named the previous tool while the sidebar already highlighted the fourth file, and the lag compounded rather than settled: the budget grows at a fixed 200 characters a second, so a model generating faster than that never lets the walk catch up. The walk now continues past the overrun with a zero remainder — text after the cut comes back empty and is filtered out of the console, while `tool` and `failover` entries always pass through in full. The typing speed is untouched by design; what changed is ordering, so the header count, the current tool and the failover divider are live while the prose behind them is still being typed. Two consequences are deliberate: a tool row can now appear beside a half-typed paragraph, and the same paragraph flickers in and out of the row list as it fills — which is exactly why the console keys every row off its index in the _source_ transcript rather than off its position in the filtered list. `toolCallId` was the obvious key for tool rows and was rejected: the ledger is not cleared on a failover, so a backend that numbers its calls deterministically (`call_0`, `call_1`, …) would collide across the hop — the mock scopes its ids per stream for exactly that reason. The invariant that makes the source index usable as a key — that `revealTranscript` returns one entry per input entry, at the same index, for every budget — is asserted in `lib/review/transcript.test.ts` rather than left to the reader, because the moment the ledger starts deleting entries the key silently starts pointing at the wrong row.
- **Uncaught server and render errors funnel through `onRequestError`** in the root `instrumentation.ts` — the single capture point that logs the error, its `digest` and the route context. It is guarded to the Node.js runtime so the `pino` import never reaches an edge bundle. The share-page client `error.tsx` surfaces that `digest` in its UI so a user can quote it and correlate their report with the server log.
- **The probe that speaks for the container deliberately knows nothing about the datastores.** The `HEALTHCHECK` in the `Dockerfile` is the only caller of a health route: it fetches `/api/health/live`, which has no dependencies and answers 200 whenever the server is listening. That is the right shape for a probe whose verdict is about the _process_, because the review flow survives a dead Redis by design — the limiter fails open (§6) — and a container that still serves reviews should not report itself broken. The deeper check lives in `/api/health/ready`, which asks Postgres and Redis and logs which one failed; it is wired to nothing today, for the reason recorded in §6.
- **Error-tracking (Sentry/GlitchTip) is deliberately deferred** behind the `onRequestError` seam: the choke point exists, the external dependency and DSN do not, until prod volume justifies them.
- **A nonce-based strict CSP is set per request in `proxy.ts`** (the Next 16 rename of `middleware.ts`), the industry-standard approach recommended by Next.js, OWASP and web.dev. Each request gets a fresh CSPRNG nonce; the nonce is put on the request so Next stamps it onto its own framework and bundle scripts, and the same `Content-Security-Policy` is set on the response. `script-src` is `'self' 'nonce-…' 'strict-dynamic'`: `'strict-dynamic'` discards host allowlists and trusts only the nonced bootstrap plus whatever it loads, so an injected `<script>` without the unguessable nonce cannot run. The app is already dynamic per request (mock/real reviews, DB-backed share pages), so the dynamic-rendering that nonces require costs us almost nothing — the root layout `await connection()`s, opting every route into per-request rendering so each gets a fresh nonce (a client-component page such as the home screen cannot host `connection()` itself, and `export const dynamic` is ignored there, so the shared layout is the single correct choke point).
- **`style-src` is `'self' 'unsafe-inline'` with no nonce, deliberately.** Shiki paints syntax tokens with inline `style="color:…"` attributes and the UI uses React `style={{}}`; a nonce cannot cover style _attributes_, and per spec a browser that sees both a nonce and `'unsafe-inline'` in `style-src` ignores `'unsafe-inline'`, which would silently break highlighting. Inline styles cannot execute code, so this is a low risk. `'wasm-unsafe-eval'` stays in `script-src` for Shiki's Oniguruma WASM; `'unsafe-eval'` is added only in development (React refresh/HMR needs it) and never ships to production.
- **Flat, static headers live in `next.config.ts` `headers()` on `/(.*)`** so they cover every response including static assets that the CSP matcher skips: `X-Frame-Options: DENY` and CSP `frame-ancestors 'none'` together forbid framing (clickjacking); `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; a `Permissions-Policy` that turns off clearly-unused features (camera, microphone, geolocation, payment, usb, motion sensors) while deliberately leaving clipboard alone because the copy button uses `navigator.clipboard.writeText`; and `Cross-Origin-Opener-Policy`/`Cross-Origin-Resource-Policy` set to `same-origin` (COEP is intentionally omitted — `require-corp` would break subresources).
- **HSTS is `max-age=63072000; includeSubDomains` without `preload`.** Preloading is near-irreversible (removal from the browser preload list takes months), so it is left off deliberately. If the edge (Traefik/Coolify) already emits HSTS, drop the app-level header to avoid a duplicate.
- **The private-PR gate returns 403 (not 404)** for an anonymous request against a private PR that the server `GITHUB_PAT` can read, which discloses the repository's existence to an anonymous prober. This is an accepted trade-off, not a fix left undone: the primary control is scoping `GITHUB_PAT` to `public_repo` (per `.env.example`), under which GitHub returns 404 for every private repo, the metadata fetch never surfaces a private PR, and this branch is never reached. Given that scoping, the 403-with-private-card response is kept deliberately for its clearer UX.
- **The credentials a user brings live in `Home`, and `reset` clears them while keeping the choice that selected them.** The Anthropic key, the GitHub PAT and the premium checkbox used to be `useState` inside `IdleScreen`, which unmounts whenever the run screen is shown — so "Edit URL" and the header's home button dropped all three, and the PAT case was merely loud (the field is `required`, so the browser blocks the submit) while the key case was silent and worse: the checkbox reset too, the field disappeared, `required` had nothing to enforce, and the next "Review" quietly ran the free chain for a user who had deliberately supplied a key for Sonnet. All three now sit beside `url` and `visibility` in `Home`, so returning to the form keeps the premium checkbox ticked and its field visible and `required` — a silent downgrade is no longer reachable. The two secrets themselves are wiped on the way back, because the form promises "used in-memory for this request only, never stored" and that promise is kept by clearing rather than by rewording: the user re-enters the secret, which is a keystroke cost paid to keep a security claim literally true. "Try again" is a different path and deliberately unaffected — it replays `lastRunOptionsRef`, the options the run was started with, so a retry after a provider hiccup does not ask for the key again.

## 8. Naming

- **Files and folders** — `kebab-case`.
- **Types and interfaces** — `PascalCase`, no `I` prefix.
- **Fields** — `camelCase` in the domain and UI; `snake_case` only at external boundaries.
- **Components** — file in `kebab-case`, export in `PascalCase`. **Hooks** — `use` prefix.
- **Factories** — a single prefix (`create`).
- **Role suffixes in file names** (for example, for schemas) — selectively, only where the file's role is otherwise unclear. Co-location by default, without extracting types wholesale into separate files.
- **Constants** — `UPPER_SNAKE_CASE`. **Model tool names** — `snake_case`, namespaced.

## 9. Tests

- **The suite reaches nothing outside the process — no Postgres, no Redis, no network — and that is a property to preserve, not a coincidence.** `npm test` runs vitest in the `node` environment against `**/*.test.ts`, with `.claude/**` and `.next/**` excluded so a linked worktree cannot mix two branches into one run. Everything that would open a socket is replaced at the module boundary: `@/lib/redis` in `lib/rate-limit.test.ts`, `app/api/review/route.test.ts` and `lib/review/run-review.test.ts`, `@/lib/db/reviews` in the orchestrator test, and the leaf GitHub calls (`get-pr-metadata`, `get-file-contents`, `list-directory`) in `lib/github/octokit/index.test.ts`. `import "server-only"` is aliased to `test/server-only.ts` so server modules can be imported directly.
- **The orchestrator is tested through the mock stand the app already ships, not through a parallel harness.** `lib/review/run-review.test.ts` calls `runReview()` as a function under `MOCK_REVIEW=1 MOCK_OFFLINE=1`, reads the SSE body by hand and asserts on the `data-*` frames. The scenarios come from `lib/review/mock/scenario.ts` (`finish-length` for the cut-short path, `finish-length-read-all` for the same cut after every diff has been read) and `lib/review/mock/injected-error.ts` (`MOCK_ERROR=first-only` for an ordinary hop); the GitHub side is `createFixtureGithubAccess`. What this buys is the one invariant nothing else guards: `messagesDroppedByHandoff` (`lib/review/mock/step-result.ts`) plants an orphaned `tool-call` id and a reasoning-plus-empty-text assistant message in the first step, and three assertions fail if `sanitizeForHandoff` stops dropping them — which in production is a 400 from Cerebras or Groq on the very hop that was supposed to rescue the review. The same stand pins what only a real transcript can prove about the handoff nudge: that the requested and unrequested file lists are computed from actual tool calls, that generated files are excluded, and that a second hop leaves exactly one nudge in the array; the nudge's own text — all four output shapes, both `file:line` forms, the refusal sentence and the sanitization of interpolated names — is pinned by `lib/review/system-prompt.test.ts` against the pure function directly, so that half of the coverage survives the mock stand's removal. `prepareStep` is reached by recording the options every attempt is called with and invoking the returned function for step 0 — the mock stream itself does not honour `prepareStep`, so the assertion is on the settings handed to the SDK, not on their effect.
- **Strategy is chosen at module scope, so a test that changes the environment must reload the module.** `run-review.ts` picks `streamTextMock` versus `streamText` and offline versus real GitHub at import time, and `lib/rate-limit.ts` builds its limiters the same way; both test files therefore pair `vi.stubEnv` with `vi.resetModules()` and a dynamic `import`. Two consequences bite anything written later: `importOriginal` inside a `vi.mock` factory is **not** re-evaluated by `resetModules`, so a mock that wraps a module which reads `env` will keep serving the environment of the first test in the file; and a class imported statically by the test file belongs to the pre-reset graph, so `instanceof` against the reloaded graph fails — the GitHub error used in the pre-stream test is imported _after_ the reset for exactly that reason.
- **Timing is faked, never waited out.** The mock stream pauses 150–500 ms per event, so one three-provider run is about ten seconds of wall clock; the orchestrator test runs the reader concurrently and drives it with `vi.advanceTimersByTimeAsync`, which brings the file to well under a second. `withRetry` (`lib/github/octokit/index.ts`) seeds its backoff with unseeded jitter, so its tests are on fake timers too — a real sleep there would be non-deterministic, not merely slow.
- **The rate limiter's Lua is covered by its arguments and by a transliteration, not by a Lua runtime.** Two failure modes are separated on purpose: `check()`'s own behaviour (allow, refuse without consuming, `retryAfterMs`, `blockedTier`, fail-open on a throw, on a not-ready client and on the half-second eval timeout) is asserted against a stubbed `eval`; the ARGV layout is asserted independently, tier by tier, at the indices `ARGV[2*i+1]`/`ARGV[2*i+2]` the script reads, so shifting the array by one — the exact defect a careless move to `redis.call('TIME')` would introduce — reddens a test instead of silently applying an hourly window to a daily budget. On top of that, a JS transliteration of `CHECK_AND_CONSUME` drives a fake sorted set from the real `KEYS`/`ARGV` and plays out the production tiers: eight an hour, ten a day, nothing consumed while refusing, and the longer of the two waits quoted when both tiers are full. Executing the Lua string itself would need a Lua runtime in `devDependencies`, which is not worth one script.
- **What is deliberately left uncovered.** `lib/review/stream.ts` is types plus one constant and cannot be meaningfully tested; `app/api/health/live` has no branches; `lib/db/reviews.ts` is not exercised against a real Postgres — the part that can be got wrong silently is the idempotency key, and that is pinned by golden values in `lib/db/slug.test.ts`; the error-suppression window in `lib/redis.ts` only changes log volume; and the field mapping in `get-pr-files`/`get-pr-metadata` is flat transcription that `tsc` already guards, while the valuable half of those modules — error translation — has its own file. The React components and hooks under `app/` are outside the node-environment suite entirely, which is why the global line percentage sits near 50 while the server modules the epics care about sit far higher. The orchestrator itself is covered on its happy and failover paths but not wall to wall (~80% of statements): the refusal branches ahead of the stream (limiter, both size gates), the over-budget pre-flight swipe, the terminal chain-exhausted path and the stream's `onError` closure run only in production — the mock harness never steers into them.
- **Coverage is measurable but not enforced.** `npm run coverage` runs the suite through `@vitest/coverage-v8`; the config names the provider and the `include`/`exclude` sets and stops there. No thresholds are wired in, because a number that fails CI would have to be set above the UI-dragged global figure to mean anything, and setting it there would be a promise the suite does not keep. The report is the artefact; `/coverage` is gitignored. Changing dependencies for this — or for anything — pulls in the lock ritual: `npm install` writes a macOS-flavoured lock, and `npm run lock:linux` has to rebuild it under `node:26-slim` or CI and the image drift apart.

## 10. What we deliberately don't do

Anti-overengineering for a project of the current size (one dominant feature):

- **No** `features/` or `src/` — an extra layer for a single-feature app.
- **No full hexagon / DDD** with use-case layers and behavior-rich domain classes: the entities have no invariants, this is data-in / data-out. Ports exist only for external services.
- **No centralized types folder** — co-location next to the code.
- **No barrel files** in client paths; they are acceptable only as the public entry point of a server-only module.
- **No abstractions or dependencies added in advance** — they are introduced when the simple solution is no longer enough.
